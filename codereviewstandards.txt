1. Rationale code, don't vibe code.

No code changes should be made until you have thought through the problem, questioned the reasoning, and explicitly decided what should change via your own judgment.

2. Inspect for duplication first.

   If the system already knows, calculates, stores, or determines something, don't make another component independently reproduce that knowledge without a reason.

   Duplication must have a rationale. If there is no reason for it, remove it or move the responsibility to the appropriate component.

3. Inspect memory allocation.

   Ask what information the system is holding, how much, where it is held, how long it needs to exist, and whether it needs to exist at all.

   Do not treat stored state as free. Every piece of retained information should have a rationale.

4. Inspect temporal access.

   Use the MDATO method — Memory, Data, Access, Transitions, Output.

   Ask:

   * What is in memory?
   * What data does the system contain?
   * Who or what can access that data?
   * How does the data transition or transform from one place to another?
   * What does the system ultimately output?

   Consider not only what can access information, but when that access is possible and when that information ceases to be relevant.

   Enforce invariants at the boundary.

   An object must be valid from the exact moment of its construction. Never permit a component to exist in an indeterminate or corrupted state.

   If initialization inputs or state mutations violate system rules, reject the change immediately at the boundary (e.g., via guard methods or immediate exceptions) before allowing that state to transition, propagate, or be accessed by downstream components.

5. Optimize for efficiency with intention.

   Efficiency is not synonymous with rigid minimalism. Go lean when the system benefits from being lean; go bulk when additional structure, capacity, redundancy, or computation serves a purpose.

   Optimize according to the objective, the constraints, and the circumstances.

   Prudence determines what should be optimized, how aggressively it should be optimized, and whether optimization is warranted at all.

6. Inspect time complexity.

   Ask how the computational cost of an operation changes as the amount of input grows.

   Identify operations whose time requirements scale poorly, and determine whether that cost is justified by the system's purpose and constraints.

   Do not optimize complexity for its own sake. An inefficient algorithm may be perfectly appropriate for a small or bounded input, while an apparently reasonable operation may become a serious problem at scale.

7. Label.

   Identify what each component is supposed to be and what responsibility it is supposed to hold.

   Review top-down: identify the system, inventory its components, label their intended identities and relationships, then compare those labels against what the code actually does.

   Identity precedes the determination of location. Know what something is by its label or pseudocode before determining where its responsibilities belong.

   If you can't label it, you probably don't know it.

   Distinguish where code is declared from when it executes.


8. Write.

   Programmers should be writers/essayists.

   Coding is about what the code represents, not the code itself. The programmer should therefore be able to posthumously describe the system they have built: what it is, what it contains, how it operates, how information moves through it, what each component represents, and why it behaves the way it does.

   Once the system has been reviewed, produce a detailed, illustrative report of everything that happened, by hand.

   Your document should not just be the code itself. Describe the operation of the system vividly as a play-write would a story.

   Explain:

   * what the system is;
   * what it does;
   * what was changed and why;
   * and what the system ultimately represents.

   The report should allow someone, even a layman, to understand the operation of the system without having to reconstruct the programmer's thinking from the source code alone.

   Writing is therefore not documentation after programming.

   Writing is a method of understanding the program itself.

   A programmer should be able to move between representations:

   System → Concept → Pseudocode → Code → Operation → Explanation.

How to use these methods to review

1. Inventory the files.
2. Identify what each file is supposed to do.
3. Identify how the files relate to one another.
4. Trace the major flow of data through the system.
5. Apply the review standards where they are relevant.
6. Record the discoveries, decisions, changes, and reasoning.
7. Produce a detailed illustrative report of what the system represents and what happened during the review.

Label → Locate → Choose the tool → Inspect → Decide → Explain.
